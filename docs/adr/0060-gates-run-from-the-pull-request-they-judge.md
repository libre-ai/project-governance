# ADR-0060 — Les gates s'exécutent depuis la pull request qu'ils jugent : options mesurées

- **Statut :** proposed — la fusion de cette pull request signe la mesure et l'écartement conditionnel d'A1, tant que les deux comportements de GitHub qu'il suppose ne sont pas mesurés. Aucune option n'est retenue ; le choix d'une option se fera par un ADR ultérieur. Cet ADR ne modifie aucun workflow ni aucun gate.
- **Arbitrage :** décision du propriétaire du 2026-10-24 sur la question P1 des revues (ce que signe la fusion), prise par question structurée et relayée par la session de coordination : « Signe la mesure ».
- **Date de rédaction :** 2026-10-24
- **Origine :** inspection — issue #152, relevés de revue de #141 et #142, limite déclarée par #144, incidents corrigés par #151 et #154.
- **Portée :** les workflows de ce dépôt qui jugent une pull request, requis ou non. Les dépôts de la flotte ne sont pas concernés, sauf en tant que contenu lu par les gates de flotte.
- **Numéro :** 0059 est laissé à l'amendement d'ADR-0056 rédigé en parallèle.
- **Invariants :** aucun invariant modifié.

## Contexte

### Le problème, tel que l'issue #152 le pose

Sur `pull_request`, chaque workflow de ce dépôt extrait la merge ref et exécute le code du gate qui s'y trouve. Une pull request peut donc modifier le code ou les données du gate qui la juge, et passer son propre check requis. Trois constats de revue l'ont montré le 2026-10-23/24 :

- #141, premier tour, constat 7 : `pr-door.yml` exécute `check-pr-door.ts` depuis la branche de la pull request ; une pull request peut éditer le gate Door et passer « Door declaration ».
- #142, premier tour : en CI, `check-review-evidence.ts` a imprimé une surface qui incluait le fichier qu'il ajoutait, et a répondu « touches none » pour une pull request qui modifiait `check-review-evidence.ts` lui-même.
- #144 : le gate Not-added lit ses règles à la merge base, mais son code s'exécute depuis la tête, et son en-tête le déclare comme limite.

L'inverse tient aussi : les gates qui lisent la flotte à la tête de la branche servie ne voient rien de la pull request. Le gate SQL était vert sur #141 et rouge sur la branche servie après sa fusion (`exec-non-constant` à `0fe0a6371c01:tools/quality/check-pr-door.ts:258`, corrigé par #151) ; le gate de contexte était vert sur #142 et rouge après sa fusion (`AGENTS.md` à 81 lignes pour un plafond de 80, corrigé par #154).

## Options

Le coût est compté en fichiers de workflow touchés, mesurés sur l'arbre de `066ef494ff33`. Aucune option n'est appliquée par cet ADR.

### Option A — Exécuter le gate depuis la base, lire la pull request comme donnée

#### A1 — `pull_request_target`

**Forme.** Déclencheur `pull_request_target` avec les mêmes `types:` ; `permissions: contents: read` au niveau du job, rien d'autre ; extraction de `github.event.pull_request.base.sha` pour `tools/` et les données ; tête de la pull request récupérée dans un dépôt git séparé, lue seulement comme objets (`git diff base...head`, `git cat-file`) ; description lue dans le payload. Aucun `bun install`, aucun `bun run` résolu depuis le `package.json` de la pull request, aucun processus Bun dont le répertoire de travail est un arbre de la pull request.

**Coût mesuré.** Applicable à 3 des 6 checks requis : `pr-door.yml`, `pr-negatives.yml`, `pinned-citations.yml`, plus l'étape `check-review-evidence.ts` extraite de `ci.yml` vers un workflow neuf. Total : 4 fichiers modifiés ou créés, 5 si l'on compte `ci.yml` amputé, et un contexte requis de plus dans le ruleset, acte du propriétaire. `pinned-citations.yml` doit en outre perdre son `issues: write` de niveau workflow au profit d'un job séparé pour `schedule` et `workflow_dispatch`. Inapplicable à `Bun quality`, `composition / validate` et `Composed targets…`, dont l'objet est d'exécuter du code (constat 2).

**Sécurité.** Le risque classique de `pull_request_target` : le job tourne dans le contexte de la branche par défaut du dépôt, avec ses secrets et son jeton, au-dessus d'une tête que son auteur contrôle. La documentation GitHub dit « This event runs in the context of the default branch of the base repository », avec `GITHUB_SHA` égal au dernier commit de la branche par défaut ; c'est documenté, non mesuré ici. Ce n'est pas la base de la pull request : les deux coïncident ici, puisque la branche par défaut est `migrate/recover-code` (`gh api repos/libre-ai/project-governance --jq .default_branch`), mais une pull request vers `main`, qui existe (`git ls-remote --heads https://github.com/libre-ai/project-governance main`), serait jugée par le workflow de la branche par défaut. Secrets mesurés : 0 au niveau du dépôt ; ceux de l'organisation sont `unavailable` (mesure ci-dessus). Le jeton par défaut du dépôt est en lecture (mesure ci-dessus), mais un workflow peut l'élever, et une seule étape qui exécute un contenu de la pull request — installation, script `package.json`, `preload` d'un `bunfig.toml`, `.env` lu par Bun — devient une exécution de code dans le contexte de la branche par défaut. Le cache d'Actions est partagé avec la branche par défaut (documenté par GitHub, non mesuré ici) : une étape qui y écrit à partir de données de la pull request l'empoisonne. Le gate `pinned-citations` passe du texte écrit par l'auteur à git ; il est durci (`066ef494ff33:tools/quality/check-pinned-citations.ts:145-155`), mais son rayon d'impact monte avec le contexte. Enfin l'option va contre la position écrite du gabarit du lien de work package (fait ci-dessus).

**Ce qu'elle ferme.** Pour ces quatre gates : la pull request ne peut plus modifier ni leur code, ni leurs données, ni leur fichier de workflow, ni le script `package.json` qui les lance, puisque `pull_request_target` lit le workflow de la branche par défaut (documenté, non mesuré ici).

**Ce qu'elle laisse ouvert.** (i) Une pull request peut ajouter un job `pull_request` portant le même nom qu'un check requis ; les deux sont émis par GitHub Actions (constat 3), et la résolution n'est pas mesurée. (ii) Le rattachement d'un run `pull_request_target` au sha de tête, et sa prise en compte pour un contexte requis, ne sont pas mesurés ici. (iii) Les trois checks qui exécutent du code restent entiers. (iv) Une pull request qui corrige un de ces gates est jugée par l'ancien ; son nouveau comportement n'est vu qu'après la fusion, ce qui déplace l'angle mort inverse à l'intérieur de ces gates. (v) L'application de la politique d'approbation des forks à `pull_request_target` n'est pas vérifiée (hypothèse en fin d'ADR).

#### A2 — variante sans changer de déclencheur : outillage de la base sous `pull_request`

**Forme.** On garde `pull_request`. On extrait l'outillage à `github.event.pull_request.base.sha` dans `$RUNNER_TEMP` et on l'exécute depuis ce répertoire, selon le motif de `066ef494ff33:.github/workflows/reusable-work-package-link.yml:81-96`, en lisant l'espace de travail de la pull request par son chemin absolu. Pour `composition / validate`, `tooling_ref` vaut le sha de base au lieu de `github.sha` (`066ef494ff33:.github/workflows/code-validation.yml:16`). Ce seul changement ne suffit pas. `run-composition.py` lit `manifest.json` à côté de son script, donc dans l'outillage (`066ef494ff33:.github/composition/run-composition.py:15`, `066ef494ff33:.github/composition/run-composition.py:23`). Avec l'outillage de la base, ce check composerait les autres dépôts aux refs du manifeste **de la base**, et une pull request qui change `manifest.json` ne serait plus composée telle qu'elle la déclare. A2 y rouvrirait la classe de l'option D. `run-composition.py` doit donc recevoir le manifeste de la pull request comme donnée, par un argument, comme `generation-coherence.yml` ci-dessous. Cet argument a deux conséquences hors du script :

- son seul appelant dans ce dépôt est `validate-composition.yml` (`066ef494ff33:.github/workflows/validate-composition.yml:74-76`, `066ef494ff33:.github/workflows/validate-composition.yml:141-143` ; `git grep -n run-composition.py 066ef494ff33 -- .github/workflows`), qui doit le passer. Deux dépôts de la flotte appellent aussi `run-composition.py` directement en ligne de commande, chacun deux fois : `libre-ai/application-development-toolkit@4e782fd5c5cc:.github/workflows/playwright-guid-diagnostic.yml:42,57`, avec l'outillage extrait à `8a27b8f5bf77` (`libre-ai/application-development-toolkit@4e782fd5c5cc:.github/workflows/playwright-guid-diagnostic.yml:35`), et `libre-ai/personal-knowledge-workspace@855fee670706:.github/workflows/notebook-webkit-macos.yml:49,77`, avec l'outillage à `75d6ea085b18` (`libre-ai/personal-knowledge-workspace@855fee670706:.github/workflows/notebook-webkit-macos.yml:42`). Relevé de la revue du troisième tour (`docs/reviews/adr-0060-gates-run-from-pr-2026-10-24/REVIEW-ROUND-3.md`, T4), rejoué sur ces deux fichiers. Le nouvel argument de la ligne de commande de `run-composition.py` doit donc être facultatif, et son absence doit garder le manifeste de l'outillage ; sinon ces deux dépôts cassent au prochain relèvement de leur épingle. Le compte de fichiers ci-dessous porte sur ce dépôt et ne change pas. Sa seule extraction est l'outillage (`066ef494ff33:.github/workflows/validate-composition.yml:58-65`), donc il lui faut aussi une étape qui obtienne le manifeste de la pull request. Ce workflow est un `workflow_call` appelé par 14 dépôts non archivés de la flotte, 16 avec les deux archivés (`ai-practice-workbench`, `information-feed-filter`), tous épinglés à un sha complet. Premier instrument, l'index de recherche de code, qui peut retarder et ne voit pas les deux archivés : `gh search code --owner libre-ai "project-governance/.github/workflows/validate-composition.yml" --limit 100 --json repository,path --jq '[.[]|select(.path|startswith(".github/workflows/"))|.repository.nameWithOwner]|unique|length'` → 14. Second instrument, l'arbre de la branche servie de chaque dépôt du registre, cloné : 16 (`REVIEW-ROUND-3.md`, T4). Les deux archivés sont épinglés à `7c2238d6185e` (`gh api repos/libre-ai/ai-practice-workbench --jq .archived` → `true`, idem pour `information-feed-filter`) ; un dépôt archivé n'exécute plus de workflow. Son interface est un contrat : l'entrée nouvelle doit être facultative, et son absence doit garder le manifeste de l'outillage, qui est le bon pour ces dépôts.
- `download-advisory-database.py` charge `run-composition.py` comme module et appelle `runner.load_plan(target, revision)`, qui lit le manifeste de l'outillage (`066ef494ff33:.github/composition/download-advisory-database.py:16`, `066ef494ff33:.github/composition/download-advisory-database.py:73`, `066ef494ff33:.github/composition/run-composition.py:21-23`). Sans changement, la base d'avis serait choisie sur le manifeste de la base et la composition sur celui de la pull request.

**Coût mesuré.** 9 fichiers, dont 7 workflows et 2 scripts :

1. `pr-door.yml` ;
2. `pr-negatives.yml` ;
3. `pinned-citations.yml` ;
4. `ci.yml` (étapes `check-review-evidence`, `check-audit-delta`, monotonie des refs, chemins composés) ;
5. `generation-coherence.yml` (script de la base, manifeste de la pull request lu comme donnée) ;
6. `code-validation.yml` (`tooling_ref` à la base) ;
7. `validate-composition.yml` (étape qui obtient le manifeste de la pull request, entrée facultative, argument passé aux deux appels) ;
8. `run-composition.py` (manifeste reçu en argument, `066ef494ff33:.github/composition/run-composition.py:21-23`) ;
9. `download-advisory-database.py` (manifeste transmis à `load_plan`).

Le minimum est 8 si `download-advisory-database.py` reste inchangé, au prix de l'incohérence ci-dessus. Si l'argument devient un paramètre obligatoire de `load_plan`, les cinq appels de `066ef494ff33:.github/composition/test_run_composition.py` changent aussi, soit 10 fichiers (`git grep -n load_plan 066ef494ff33 -- .github/composition`). `bun run check` reste celui de la pull request : ce sont ses propres tests.

**Sécurité.** Aucun changement de jeton ni de contexte : tout reste en lecture, comme aujourd'hui.

**Ce qu'elle ferme.** La modification accidentelle du code ou des données d'un gate qui passe son propre check — les cas #141 constat 7 et #142 — pour les gates déplacés.

**Ce qu'elle laisse ouvert.** Le fichier de workflow reste celui de la merge ref : une pull request peut réécrire le workflow pour exécuter son propre outillage. Le contournement délibéré reste possible, mais il doit passer par `.github/workflows/`, une surface plus petite et visible au diff. Comme A1, le gate modifié par une pull request est jugé par l'ancien.

**Combinaison A2 + B restreint à `.github/workflows/`.** Un échec fermé limité à ce répertoire rendrait fermé par défaut le contournement qu'A2 laisse visible. Friction mesurée : 30 des 146 commits de la branche servie depuis le 2026-09-24 touchent `.github/workflows/` (`git log --since=2026-09-24 --format=%H origin/migrate/recover-code -- .github/workflows | wc -l` → 30), et 19 touchent les sept fichiers des checks requis (`git log --since=2026-09-24 --format=%H origin/migrate/recover-code -- .github/workflows/code-validation.yml .github/workflows/validate-composition.yml .github/workflows/generation-coherence.yml .github/workflows/pr-door.yml .github/workflows/ci.yml .github/workflows/pinned-citations.yml .github/workflows/pr-negatives.yml | wc -l` → 19). Si le garde est porté par `check-review-evidence.ts`, qu'A2 déplace vers l'outillage de la base, son code s'exécute depuis la base ; le workflow qui lance le garde reste celui de la merge ref, et c'est précisément la surface gardée. Les autres limites de B ci-dessous s'appliquent.

### Option B — Échec fermé sur la surface d'un gate, sauf `Owner-arbitration:`

**Forme.** Une pull request qui modifie le code ou les données d'un gate — `.github/workflows/`, `.github/composition/`, `tools/`, les `ecosystem/*.ts` et leurs données, `package.json`, `bun.lock`, `bunfig.toml` — échoue sur ce gate, sauf si sa description ou une ligne qu'elle ajoute porte `Owner-arbitration: AAAA-MM-JJ`, sur le modèle de `check-review-evidence` (`066ef494ff33:tools/quality/check-review-evidence.ts:28-38`, surface `066ef494ff33:tools/quality/check-review-evidence.ts:94-117`).

**Coût mesuré.** 0 workflow si la surface est ajoutée à `check-review-evidence.ts`, déjà lancé par `066ef494ff33:.github/workflows/ci.yml:222` ; 1 si c'est un gate distinct. Friction, sur les 146 commits de la branche servie depuis le 2026-09-24, chacun ayant exigé le marqueur :

- 87 pour le seul code (`tools/`, `.github/`, `ecosystem/*.ts`, `package.json`, `bun.lock`, `bunfig.toml`, commande ci-dessus) ;
- **103** pour la surface décrite ici, code et données de gate d'`ecosystem/` : `git log --since=2026-09-24 --format=%H origin/migrate/recover-code -- tools .github 'ecosystem/*.ts' package.json bun.lock bunfig.toml ecosystem/repositories.v1.yaml ecosystem/fleet-pins.v1.yaml ecosystem/sql-construction-allowlist.v1.yaml ecosystem/web-headers-allowlist.v1.yaml ecosystem/release-age-exceptions.v1.yaml | wc -l` → 103 ;
- **104** si l'on ajoute le code de gate hors de `tools/` et d'`ecosystem/` (`crates/ecosystem-engine/scripts`, lancé par `check:vendored` et `check:patch-rev` ; `distribution/*.ts`, lancé par `feeds-freshness.yml` ; `brand/*.ts`, lancé par `check:brand`) : même commande, avec `crates/ecosystem-engine/scripts 'distribution/*.ts' 'brand/*.ts'` en plus → 104.

**Sécurité.** Aucun jeton nouveau. Le marqueur est une convention de texte écrite par l'auteur de la pull request, et le gate le dit lui-même (`066ef494ff33:tools/quality/check-review-evidence.ts:28-38`) : quiconque ouvre la pull request peut l'écrire. Sous `pull_request`, le garde s'exécute depuis la tête : une pull request peut retirer un chemin de la surface dans la même pull request qui modifie ce chemin, ce que #142 rend possible : elle a ajouté deux chemins à la surface, lue à la tête, dont `tools/quality/refusals-exemptions.v1.json`, que la même pull request créait (`git show --stat e04890236623`, `git show e04890236623 -- tools/quality/check-review-evidence.ts`). Le retrait est une inférence de l'issue #152, pas une observation. Lire la surface à la merge base, celle de `origin/<base>` avec la merge ref (note sous le tableau des checks requis), comme `pr-negatives` lit ses règles (`066ef494ff33:tools/quality/check-pr-negatives.ts:115-118`), le réduit sans le fermer : le code reste celui de la tête.

**Ce qu'elle ferme.** L'auto-validation silencieuse : une pull request qui touche un gate rougit ou porte un marqueur, et le propriétaire le voit à la fusion.

**Ce qu'elle laisse ouvert.** Le contournement délibéré (éditer le garde ou le workflow). À 103 sur 146, le marqueur deviendrait routinier, ce qui en vide le sens d'arbitrage. Et une session d'agent qui modifie `tools/` n'a pas le droit d'écrire ce marqueur sans arbitrage réel : chacune de ses pull requests attendrait le propriétaire.

### Option C — Statu quo documenté, la revue humaine comme seule garde

**Forme.** Aucun changement de workflow ; la limite est écrite dans l'en-tête de chaque gate requis, comme `066ef494ff33:tools/quality/check-pr-negatives.ts:117-118` le fait déjà.

**Coût mesuré.** 0 workflow ; 6 en-têtes de gate, ou ce seul ADR accepté.

**Sécurité.** Inchangée. État mesuré : le code de la pull request s'exécute avec `contents: read` dans les six checks requis ; `inventory-drift` et `context-conformance` exposent un `GH_TOKEN` portant `issues: write` à chaque étape, donc au code de la pull request pour une branche du dépôt ; parmi les workflows `pull_request`, 8 extractions laissent le jeton dans `.git/config` : deux de checks requis, `Door declaration` et `Bun quality` (`066ef494ff33:.github/workflows/pr-door.yml:32`, `066ef494ff33:.github/workflows/ci.yml:158-160`), et six de jobs non requis, `Licensing and contribution governance`, `inventory-drift`, `context-conformance`, `context-hygiene`, `doctrine-governance` et `feeds-freshness` (`066ef494ff33:.github/workflows/ci.yml:29-31`, `066ef494ff33:.github/workflows/inventory-drift.yml:44`, `066ef494ff33:.github/workflows/context-conformance.yml:50-52`, `066ef494ff33:.github/workflows/context-hygiene.yml:24`, `066ef494ff33:.github/workflows/doctrine-governance.yml:25-27`, `066ef494ff33:.github/workflows/feeds-freshness.yml:32`). Relevé : pour chaque `actions/checkout@` des workflows qui déclarent `pull_request:`, un `awk` cherche `persist-credentials: false` avant l'étape suivante ; la commande exacte est la C8 de `docs/reviews/adr-0060-gates-run-from-pr-2026-10-24/REVIEW-ROUND-2.md`. Elle couvre aussi `validate-composition.yml`, un `workflow_call` appelé sur `pull_request`, dont l'unique extraction pose `persist-credentials: false` (`066ef494ff33:.github/workflows/validate-composition.yml:58-65`) : le compte de 8 n'en dépend pas. Une pull request de fork reçoit un jeton en lecture seule (documenté par GitHub, non mesuré ici), et la politique d'approbation vise les premiers contributeurs.

**Ce qu'elle ferme.** Rien mécaniquement. La garde est la fusion par le propriétaire : le ruleset n'exige aucune approbation et n'admet aucun contournement. Il exige en revanche que les fils de revue soient résolus (`required_review_thread_resolution: true`) : un constat ouvert en fil bloque la fusion, mais une pull request sans revue n'a aucun fil à résoudre.

**Ce qu'elle laisse ouvert.** Tout ce que décrit l'issue : un check requis vert ne dit pas que le gate qui l'a émis est celui de la base.

### Option D — Cas inverse : les gates de branche servie lisent aussi l'arbre de la pull request

**Forme.** Sur `pull_request`, quand le dépôt inspecté est ce dépôt-ci, les gates de flotte lisent l'extraction de la pull request au lieu de `HEAD:` du distant ; les autres dépôts restent lus à leur branche servie, ce qui est correct pour eux. Cette partie « ce dépôt » devient un job à part, requérable parce qu'il ne dépend que de la pull request. Le reste d'`inventory-drift` n'est pas à requérir tel quel : son verdict dépend aussi des branches servies des 23 autres dépôts du registre (`git show 066ef494ff33:ecosystem/repositories.v1.yaml | grep -c '^  - repository: '` → 24 entrées, dont ce dépôt), qu'aucune pull request de ce dépôt ne contrôle. Ce n'est pas un job rouge en permanence : le run `push` sur `066ef494ff33` est vert, Dependabot y est `skipped` (`gh run view 40078154723 -R libre-ai/project-governance --json jobs`), et sur les 30 derniers runs `push` de la branche servie, 27 sont verts et 3 rouges (`gh run list -R libre-ai/project-governance --workflow inventory-drift.yml --branch migrate/recover-code --event push --limit 30 --json conclusion --jq '[.[]|.conclusion]|group_by(.)|map({(.[0]): length})|add'` → `{"failure":3,"success":27}`). Les 3 rouges sont `0fe0a6371c01`, `e04890236623` et `116b22bd6b0e`, la fenêtre #141 → #151 : le défaut même que D traite. Le commentaire de `066ef494ff33:.github/workflows/pinned-citations.yml:11-15`, qui dit ces gates « knowingly red », ne tient donc plus ; il est hors du diff de cet ADR.

**Coût mesuré.** 2 workflows (`inventory-drift.yml`, `context-conformance.yml`) ou 1 workflow neuf ; 11 fichiers de lecture de flotte à faire passer par un lecteur qui sait servir l'extraction locale ; un contexte requis de plus, acte du propriétaire.

**Sécurité.** Aucun jeton nouveau : lire l'extraction, c'est lire une donnée de la pull request avec le code de la pull request, comme aujourd'hui.

**Ce qu'elle ferme.** La classe #141 → #151 et #142 → #154 : un gate vert sur la pull request et rouge sur la branche servie après la fusion, pour le contenu de ce dépôt.

**Ce qu'elle laisse ouvert.** Le premier défaut, car ces gates s'exécutent toujours depuis la pull request. D est orthogonale : elle se combine avec A2, B ou C, et avec A1 si le code du gate vient de la base et l'extraction n'est lue que comme donnée.

## Ce que la mesure départage, et ce qu'elle laisse au propriétaire

- **Elle écarte A1 comme premier remède, tant que deux comportements de GitHub ne sont pas mesurés.** A1 ne couvre que 3 des 6 checks requis plus une étape ; ce qu'elle promet de fermer pour eux repose sur deux points non mesurés (le contexte homonyme émis par la même application, et le rattachement d'un run `pull_request_target` au contexte requis) ; et elle ajoute le risque d'exécution dans le contexte de la branche par défaut, contre la position écrite du gabarit du lien de work package. Les mesures se font sur un dépôt jetable, avant tout arbitrage qui retiendrait A1. Une troisième s'y ajoute, à l'état d'**hypothèse** : la politique d'approbation des workflows de fork (`first_time_contributors`) ne s'appliquerait pas à `pull_request_target`. Si elle se vérifie, la pull request d'un premier contributeur déclencherait sans approbation un job dans le contexte de la branche par défaut. Elle n'est pas vérifiée ici, et la documentation ne la tranche pas : la page « Approving workflow runs from public forks » ne mentionne pas `pull_request_target`, d'après la revue du second tour. La mesure sur le dépôt jetable reste le contrôle.
- **Elle ne départage pas A2, B et C.** Le choix dépend du modèle de menace, qui est une décision. Ce que la mesure apporte : les trois cas observés sont accidentels (deux constats de revue et une limite déclarée), et les 100 dernières pull requests fusionnées venaient toutes d'une branche du dépôt, aucune d'un fork. Contre l'accident, A2 ferme le cas pour les gates déplacés sans friction de marqueur ; B le rend visible au prix d'un marqueur sur 103 commits sur 146 (104 avec le code de gate hors de `tools/` et d'`ecosystem/`) ; A2 + B restreint à `.github/workflows/` le ferme par défaut pour 30 commits sur 146 ; C ne ferme rien. Contre un auteur hostile, aucune option qui garde `pull_request` ne ferme le cas, puisque le workflow est lu à la merge ref.
- **D ne concurrence aucune autre option.** Le défaut qu'elle traite s'est produit deux fois le 2026-10-24 (#141 fusionnée à 06:21Z, #151 à 08:18Z ; #142 à 06:33Z, #154 à 08:23Z, horodatages de `gh pr view <n> --json mergedAt`). Son coût en lecteurs est le plus élevé des options.

Questions à poser au propriétaire, indépendantes l'une de l'autre :

1. Le modèle de menace retenu pour les gates requis : accident d'un auteur de confiance seulement, ou aussi auteur hostile.
2. Le traitement du cas inverse : D, ou le statu quo avec correction après fusion comme pour #151 et #154.
