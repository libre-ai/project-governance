# ADR-0020 — Activation générale multi-repo et démantèlement du hub

- **Statut :** accepted — le merge de la pull request qui porte cet ADR est la signature propriétaire (arrêt dur du jalon γ, §5.1 du prompt de mission).
- **Date :** 2026-07-28
- **Arbitrage :** propriétaire — quatre décisions prises explicitement en session le 2026-07-28 (D1–D4), enregistrées au design d'activation (`docs/superpowers/specs/2026-07-28-multi-repo-activation-design.md`, mergé par #268 après un cycle K4 à cinq révisions et deux relecteurs indépendants) ; le présent ADR en est l'acte doctrinal.
- **Portée :** écosystème entier — topologie, invariants, séquencement, LEXICON, autorités documentaires, mécanique de migration, sécurité de la chaîne d'approvisionnement.
- **Étend :** ADR-0008 (topologie multi-repository). **Supersède de manière bornée :** voir §2 — chaque supersession est nominative et bornée à la clause près.

## 1. Contexte

Le hub `libre-ai/libre-ai` porte tout le contenu réel de la constellation (14 packages TypeScript, 7 crates Rust, 8 applications, 88 autorités de contrats, doctrine, inventaire, outillage) ; la doctrine en vigueur prévoyait une activation **par vagues** des satellites (ADR-0009 §8, ADR-0011, ADR-0018), chaque activation étant une décision propriétaire (I-17), un satellite existant d'abord comme package publié (I-16). Le 2026-07-28, le propriétaire a tranché : l'activation devient **générale** — chaque repo devient responsable de son périmètre maintenant, le hub est démantelé, la migration est intégrale en une vague. Le design mergé (#268) est la forme écrite revue de ces décisions ; le présent ADR les inscrit dans la doctrine et amende ce qui les contredit. Il régularise au passage deux dérives constatées : I-04 périmé au registre depuis l'amendement propriétaire du 2026-07-23 (ADR-0008), et l'activation de fait du repo `website` sans acte propriétaire.

## 2. Décisions

### 2.1 Les quatre décisions propriétaire (D1–D4)

| #   | Décision                                                                                                                                                                                   |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| D1  | **Activation générale** : acte doctrinal — chaque repo devient responsable de son périmètre dès maintenant ; le séquencement par vagues est supersédé                                      |
| D2  | **Hub démantelé** : `libre-ai/libre-ai` devient archive + index de migration en fin de jalon                                                                                               |
| D3  | **Deux autorités séparées** : repo `governance` (doctrine, invariants, ADR, LEXICON, index d'écosystème, schéma des fiches, outillage, evidence) + repo `contracts` (autorités canoniques) |
| D4  | **Migration intégrale en une vague** : fichiers ET code, workspaces Bun/Cargo éclatés, hub archivé en fin de mission                                                                       |

Recommandations acceptées avec le design : **un repo par package/crate pour les satellites de code partagé** (les repos produits regroupent délibérément app + crates produit + specs) ; **dépendances inter-repos par git-deps GitHub épinglées par SHA** — voir la décision de sécurité §2.5.

### 2.2 Supersessions bornées

- **ADR-0001, clause de topologie seulement** : le point « créer un nouveau monorepo » et la conséquence « l'intégration continue dans le monorepo est obligatoire » sont supersédés par D4. Les dix autres décisions d'ADR-0001 restent en vigueur. Au DECISION-REGISTER (28 entrées avant cet acte, 29 avec D29, numérotation propre au registre), seule **D07** est amendée, dans ses deux moitiés — intitulé (« One Bun and one Cargo workspace » → « un workspace Bun et/ou Cargo par repo ») et détail (« versions centralized » tombe : le catalogue central meurt avec le hub, chaque repo est responsable de ses pins). **D02 est bornée, pas amendée** : la greffe d'historique du design §5.1 est hors de son périmètre — aucun contenu legacy n'entre dans l'arbre de travail, seule la continuité d'historique des homes gelés est rétablie, et les archives restent référencées par SHA. D01–D06 et D08–D28 restent en vigueur.
- **ADR-0009** : le §8 (ordre de migration en vagues) est supersédé ; dans le §4, la seule **loi de couverture** (package publié d'abord, churn mesuré bas, exploitation couverte prouvée, métriques publiées comme précondition, clause « une large constellation est un niveau à débloquer, jamais un état de départ ») est abrogée comme précondition d'existence d'un repo ; dans le §7, la seule clause « `ecosystem/repositories.v1.yaml` est la source unique … **et des états d'exposition** » est superséée — l'état d'un projet (dont son exposition) est porté par sa fiche `project.v1.yaml`, l'inventaire restant la source unique de la **topologie**. Les §1, 2, 3, 5, 6 et 9 d'ADR-0009, le reste du §7 (publication de l'évidence — **I-20 n'est pas amendé**), et la loi d'exposition du §4 dans son principe restent en vigueur : I-13, I-14, I-17, I-18, I-19 et I-20 conservent leur source d'arbitrage intacte.
- **ADR-0011** : la partie séquencement (D1 vagues 4a/4b) est superséée ; les politiques de gate (D3 arrêt dur du lock orchestrateur, D4 confiance graduée, D6 plafonds) restent en vigueur.
- **ADR-0018** : le cadre de vagues est supersédé ; les work-packages couche 2 deviennent la roadmap du repo `orchestrator` — cohérent avec la répartition en quatre autorités séparées (Missions, Agent Orchestrator, Agent Harness, Proof/Artifact) énoncée par RFC-0001 et reprise au contexte d'ADR-0004 ; la co-localisation des spécifications harness/memory/orchestrator dans un même repo ne touche pas la séparation d'autorité d'ADR-0004 décision §2 (Missions reste l'unique autorité de workflow, quorum et autorisation d'exécution — l'orchestrateur ne peut pas s'auto-autoriser). Le D3 d'ADR-0018 (foyer de spécification `docs/apps` sous Specification Lock) est remplacé par la ventilation du design §4 ; le gate `check-specification-lock` migre vers `governance` en version cross-repo sur les specs ventilées.
- **ADR-0008** : le §5 (« tout le partagé reste au socle ») est supersédé par D1/D4 ; les points 3 et 4 sont supersédés **pour le seul cas `website`** (régularisation §2.4). Le reste d'ADR-0008 (marque option C, registre des invariants, noms conformes à l'architecture) reste en vigueur.

### 2.3 Amendements du registre des invariants

Portés à `docs/decisions/INVARIANTS.md` par la même pull request :

- **I-02** : la topologie multi-repository devient l'**état courant**, plus une cible différée ;
- **I-03** : « aucune seconde autorité » est remplacé par **deux autorités séparées** — `governance` (doctrine) et `contracts` (autorités canoniques de contrats) ; la règle « un sujet = une autorité unique » demeure, la carte d'autorité est réécrite en conséquence ;
- **I-04** : réécrit pour intégrer l'amendement propriétaire du 2026-07-23 (les noms conformes à l'architecture priment sur la préservation des URLs historiques) ; les noms d'outillage retirés restent morts, `website` excepté par la régularisation §2.4 ;
- **I-05** : « projection = artefact généré » est conservé, avec trois applications précisées — les copies vendorées de contrats sous gate de dérive sont des projections vérifiées (jamais éditées à la main, jamais canoniques) ; les repos de distribution portant des artefacts générés (`sdk-ts`, `sdk-rs`, futur `docs`) sont légitimes, leur contenu généré restant non canonique ; le site `website` est une **application** qui sert des projections, pas une « projection-repository » ;
- **I-08** : la discipline « aucun travail produit hors work-package », exécutée par le job du hub sur `apps/**`, est **remplacée par la discipline de fiche** : chaque repo produit trace ses phases, critères pondérés et preuves datées dans sa fiche `project.v1.yaml`, vérifiée par le gate cross-repo de `governance` ; le Specification Lock des contrats reste porté par le repo `contracts`. La machinerie work-package est close : `docs/transformation/work-packages.v1.json` et `G1-WORK-PACKAGES.md` deviennent des registres historiques dans `governance` (bannières posées à leur migration), le gate `check:work-packages` demeure l'exécutant intérimaire d'I-08 jusqu'à la mise en service du gate de fiche (phase 3.2), puis est retiré avec trace à l'index de migration, et la source d'arbitrage d'I-08 au registre est réécrite vers le présent ADR (le co-sourçage control-plane ADR 0047 reste documenté) ;
- **I-15** : la loi d'exposition demeure sur le fond (pas de vitrine sans vérifiable) ; son support change — l'échelle de preuve d'un projet est portée par **sa fiche**, agrégée et vérifiée par `governance` ;
- **I-16** : les quatre conditions de la loi de couverture et sa clause de clôture sont abrogées comme préconditions d'existence d'un repo ; les métriques de couverture restent des indicateurs publiés a posteriori ;
- **I-23** (note d'application, l'entrée du registre est inchangée) : **migré ≠ oublié** — l'index de migration est l'inverse fonctionnel de `FORGOTTEN.yaml` ; `check:forgotten` ne traite jamais un chemin migré comme évincé ; les `recoverable_at` restent résolubles dans l'archive clonable du hub, et le registre migré vers `governance` vérifie contre cette archive.

### 2.4 Régularisation nominative du repo `website` (I-17)

Le repo `website` a été créé et activé de fait (7 pull requests mergées dans un repo `[Reserved]`) sans acte propriétaire, en contradiction avec LEXICON §1.2/I-04, ADR-0008 pt 3 et pt 4/I-05, et I-17. Le prompt de mission γ (acte propriétaire) lui assigne la page d'accueil et les pages de comparaison : le présent ADR **régularise** cette activation — la signature propriétaire de cet ADR est l'acte. Sa description GitHub est corrigée, son rôle d'inventaire `reserved-projection-home` est réécrit (application du portefeuille qui sert des projections), et `website` sort de la liste des noms retirés pour ce seul usage.

### 2.5 Décision de sécurité — git-deps GitHub épinglées

Les dépendances inter-repos par git-deps désarment deux gardes existantes : `cargo deny check sources` (`unknown-git = "deny"`) et la quarantaine npm `minimumReleaseAge`. Bornes retenues, enregistrées ici comme décision de sécurité et non comme détail d'outillage : le `deny.toml` de chaque repo Rust ajoute `[sources.allow-org] github = ["libre-ai"]` (confiance bornée à l'organisation ; chaque bump de SHA passe par une pull request revue) ; la quarantaine ne s'applique pas aux git-deps intra-org, remplacée par le régime pin-SHA + revue ; `minimumReleaseAge` reste en vigueur pour tout paquet de registre. Les manifestes migrés sont réécrits en versions concrètes épinglées (les protocoles `catalog:`/`workspace:` ne traversent pas une git-dep) ; les contrats consommés à la compilation sont vendorés byte-exacts sous gate de dérive ; le patch cryptographique `aes` suit chaque workspace final dont le graphe contient `aes` (aujourd'hui `notebook`), tandis que `.cargo/config.toml` (+simd128) suit tout repo qui construit une cible wasm32 (`notebook` **et** `policy`) ; la liste des consommateurs de contrats est dérivée d'un relevé machine, jamais recopiée, et la clé `allow-org` est celle de cargo-deny 0.19.5, la version de la CI (mécaniques détaillées : design §5.2.3–§5.2.6). Un banc d'essai empirique (design §5.2.6, cinq cas) est un préalable du plan d'implémentation de la migration.

### 2.6 Index de migration

Le fichier `ecosystem/migration-index.v1.yaml` est institué : chaque chemin du hub → sa destination (repo cible + SHA du premier commit de destination), vérifiable par un **gate machine d'orphelins** (diff `git ls-files` ↔ index : échec sur tout chemin sans destination). Le hub passe en état « démantèlement en cours » à la première bascule, puis « archivé » en fin de mission (arrêt dur nominatif propriétaire). La règle dure de bascule s'applique : un chemin ne quitte le hub qu'après preuve verte côté destination ; les trois fenêtres de rouge structurelles sont bornées et tracées (design §5.4). La borne DCO de greffe des homes produits (design §5.1) est l'exemption nommée : **I-11 n'est pas amendée** — le DCO reste obligatoire sur toute contribution nouvelle, seule l'histoire pré-existante sort du contrôle.

### 2.7 Amendement du LEXICON

Porté par la même pull request, même procédure que la signature du LEXICON (production → revue K4 → arrêt dur → merge = signature) : noms d'autorité `governance` et `contracts` (désambiguïsation : le repo `libre-ai/contracts` et le package `@libre-ai/contracts` du repo `sdk-ts` sont deux objets distincts) ; identifiants nés après la carte (`testing`, `data`, `rgpd-kit`, `classification`, `collab-core`, `collab-relay`, `policy-core-ref`, crate `policy-core`) ; renversement assumé du §2.5 (`knowledge`, `web-platform`, `authz-biscuit`, `ecosystem-engine` deviennent des repos satellites) ; régularisation `agent-board` → `missions` (la carte rattrape l'arbitrage du 2026-07-23) ; les six noms réservés non instanciés (`proof`, `memory`, `harness`, `mcp-server`, `corpus`, `docs`) restent réservés, aucun repo créé dans γ ; les colonnes « Activation / vague » sont remplacées par un renvoi à l'index d'écosystème.

## 3. Conséquences

- `docs/decisions/INVARIANTS.md`, `docs/decisions/DECISION-REGISTER.md` (D07 amendé, note D02, entrée D29) et `docs/decisions/LEXICON.md` sont amendés par la même pull request ;
- les autorités documentaires périmées sont réécrites par la même pull request : `docs/README.md` (deux autorités ; « Topologie publique et expositions » scindé — topologie → index, expositions → fiches), `AGENTS.md` (le hub cesse d'être « the single authority » ; clause workspace alignée sur D07 amendé ; liste des noms retirés alignée sur les neuf noms morts du LEXICON §1.2 amendé — `website` en sort par la régularisation et y est nommé à part), `GOALS.md`, `STATUS.md`, `ROADMAP.md`, `docs/architecture/TARGET.md`, `docs/transformation/EXECUTION-SEQUENCING.md` (supersédé, bannière), `docs/transformation/REPOSITORY-MAP.md`, `vision.md` (sections topologie) ;
- la deny-list du gate `doctrine-governance` est étendue aux énoncés nouvellement supersédés (« tout le partagé reste au socle », « One Bun and one Cargo workspace », « la source unique … des états d'exposition ») — le gate fonctionne par motifs ;
- `ecosystem/repositories.v1.yaml` : rôle de `website` réécrit, `updated_on` daté du jour ; les ~21 repos nouveaux y entrent à leur création (checkpoint classe 9) ;
- `governance` enregistre la dépendance d'autorité amont hors organisation (control-plane ADR 0047, `constantin-jais/constantin-jais`) ;
- le système de fiches (`project.v1`), le validateur, l'agrégateur et les générateurs (design §6) sont construits dans le hub puis migrent avec `governance` ;
- les arrêts durs du jalon demeurent : création du lot de repos GitHub (classe 9), première bascule de description/dégel d'un repo produit, archivage GitHub du hub (nominatif, propriétaire).
