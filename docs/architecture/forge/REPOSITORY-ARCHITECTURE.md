# Libre-AI — Functional boundaries and existing repositories

Status: consolidation direction accepted; individual capability admission remains conditional on evidence.

## Rule

A repository boundary needs an autonomous responsibility, exercised interface, independent release and replacement needs, tests and ownership. Functional names do not automatically create repositories.

## Existing consolidation destinations

| Domain | Repository destination | Boundary |
| --- | --- | --- |
| Doctrine and portfolio decisions | project-governance | Historical governance remains available until the applicable corpus is reconciled |
| Shared schemas and SDK projections | schemas-and-contracts | Domain internals stay with their owner; only proven shared contracts enter this authority |
| Forge product and mission control | ai-work-supervision | Mission truth, decisions and integration; no ownership of application data or Git truth |
| Bounded execution | execution-sandbox plus admitted runtime modules | Confinement is distinct from an agent loop or scheduler |
| Continuity evaluation | execution-continuity-evaluator | Evaluates observed effects; does not acquire mission authority |
| Effective capabilities | capability-authorization | Validates mandates and permissions at the effect boundary |
| Model-use policy | ai-model-policy | Explains policy eligibility; does not execute capabilities |
| Integrity and provenance | artifact-verification | Does not replace functional acceptance or own product data |
| Qualification profiles | pi-evidence and domain-owned suites | The portable task contract does not depend on Pi |
| Shared application foundations | application-development-toolkit | Exercised interfaces and independently qualified consumers |
| Collaboration and data lifecycle | collaborative-data-sync, organization-data-lifecycle | Canonical objects remain with their owners |
| Public entry and publications | .github, project-website | Derived availability claims; no duplicate doctrine |
| Research | Private owner-controlled workspace | Private proposals, promoted explicitly and without raw context export |

The [repository register](../../consolidation/repository-register.json) covers observed public repositories and preserves unresolved destinations. The local design does not create forge-contracts, forge-control, live-session or work-items repositories.

## Dependency constraints

- Runtime and verification interfaces must remain usable without the Forge UI.
- UI projections do not depend on executor-specific SDKs or own mission state.
- Shared contract packages contain admitted semantics, not an accidental export of all business structures.
- Repository manifests and derived graphs cannot grant permissions.
- Product data, release channels and operating responsibilities remain independent.

Boundary extraction is justified by exercised consumers and a migration story. Until then, prefer a module in the appropriate existing family. Archiving a donor requires retained-content, consumer and restoration evidence.
